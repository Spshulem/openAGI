# OpenAGI mobile protocol

This is the one written contract for the OpenAGI daemon's mobile surface.
**Both the iOS client (Swift/SwiftUI/WidgetKit) and the Android client
(Kotlin/Compose/Glance) implement exactly this document.** They are two
completely separate codebases that never share code and never talk to each
other directly — they only agree because they both talk to this daemon the
same way.

`mobile/fixtures/` is the machine-checked half of this document. Every shape
described below has a corresponding JSON file in that directory, generated
from a real, running daemon by `scripts/generate-mobile-fixtures.mjs` — never
hand-written. `test/mobile-fixtures-current.test.js` re-generates the shape
live on every `npm test` run and fails within seconds if the daemon's actual
output has drifted from what's committed. If you change anything in this
document, regenerate the fixtures (`node scripts/generate-mobile-fixtures.mjs`)
and re-run both native clients' unit tests — a shape change here is a
client-breaking change on both platforms.

All source-of-truth line references below point at code in this repo as of
commit `136c15b`; treat the code, not this prose, as authoritative if they
ever disagree, and fix this document to match.

## 1. Pairing

Pairing has three steps: the daemon owner mints a one-time code, the phone
gets that code (via a deep link or by typing it in), and the phone exchanges
the code for a permanent node credential.

### 1.1 Mint a code

The daemon owner runs `openagi pair-phone --platform ios` (or `android`) at
the daemon's authenticated CLI, or an already-authenticated caller hits the
endpoint directly:

```
POST /nodes/enrollment-code
Content-Type: application/json
Authorization: Bearer <ownerToken>       (only if OPENAGI_AUTH_TOKEN is set)

{"platform": "mobile"}
```

Response — exactly these four keys, no token (`src/node-enrollment.js:18-31`,
`src/hosted-interface.js:985-1012`):

```json
{
  "code": "831343",
  "platform": "mobile",
  "expiresAt": "2026-09-20T02:06:59.841Z",
  "publicUrl": "https://myhost.ts.net"
}
```

The code is six digits, single-use, expires after 30 minutes
(`NODE_ENROLLMENT_CODE_TTL_MS`), and locks out for 15 minutes after 5 wrong
attempts (`src/node-enrollment.js:3-5`). `platform` for a phone is always the
literal string `"mobile"` — never `"ios"` or `"android"`. The form factor is
carried only as the node's `name` later, in the exchange call.

### 1.2 The deep link

`openagi pair-phone` prints a link the phone can open directly, built by
`buildPairingUrl` in `src/pair-phone.js`:

```
openagi://pair?url=<origin>&code=<6digits>&platform=<ios|android>
```

Example: `openagi://pair?url=https%3A%2F%2Fmyhost.ts.net&code=831343&platform=ios`

Note `platform` in the deep link IS `ios`/`android` — that is the one place
the form factor appears before enrollment; it tells the phone app which UI
copy to show, not what to send the daemon. `buildPairingUrl` also refuses to
build a link to a loopback host (a phone can never reach `127.0.0.1`) and
refuses cleartext `http://` unless the host matches the rule in §10
(`src/pair-phone.js:1-45`).

### 1.3 Exchange the code for a credential

The phone generates its own node id and node token locally, then calls the
one route that is reachable with no credential at all (`isPublicRoute` in
`src/auth.js:43-58` lists it):

```
POST /nodes/enroll/exchange
Content-Type: application/json

{
  "code": "831343",
  "platform": "mobile",
  "nodeId": "mobile:D3B1F6C2-...",
  "nodeToken": "<43-char base64url, generated by the phone>",
  "name": "Sean's iPhone"
}
```

- `nodeId` must match `/^[a-zA-Z0-9:_-]{1,240}$/`.
- `nodeToken` must match `/^[a-zA-Z0-9_-]{43}$/` (43-char base64url — e.g.
  `crypto.randomBytes(32).toString("base64url")` on the daemon side, or the
  platform's equivalent CSPRNG on the phone). The phone mints this itself; the
  daemon never generates or returns a different one.
- `name` is free text, bounded to 60 characters server-side
  (`boundedMobileNodeName`, `src/mobile-node.js:59-64`); this is the human
  device name (e.g. "Sean's iPhone"), not the platform.

Response (`src/hosted-interface.js:1102-1118`, pinned by
`mobile/fixtures/enroll-exchange.json`):

```json
{
  "node": {
    "id": "mobile:fixture-node",
    "name": "Fixture Phone",
    "platform": "mobile",
    "enrolledAt": "2026-09-20T02:06:59.841Z"
  },
  "nodeToken": "FIXTURE-SYNTHETIC-NODE-TOKEN-NOT-REAL-00000",
  "capabilities": [
    "mobile-task-client",
    "mobile-approval-client",
    "mobile-chat-client"
  ]
}
```

`nodeToken` in the response is an exact echo of what the phone sent — the
daemon does not mint a different one. If the same `nodeId` calls exchange
again with the same token it was already enrolled with, the daemon returns
this same shape with `"recovered": true` appended, instead of a 409 — an
idempotent retry after a lost response is safe.

**What each side stores after this call:**
- Phone: `nodeId`, `nodeToken`, and the daemon's origin (from the deep link's
  `url` param) — in Keychain (iOS) / EncryptedSharedPreferences or the
  platform Keystore (Android). Never in plain files, never logged.
- Daemon: the node id → token hash mapping in its node registry
  (`src/node-registry.js`), plus the enrollment's `platform`, `name`, and
  `capabilities`.

An enrollment code minted for the wrong platform, or already spent, gets a
400 (`invalid_platform`), 401 (`invalid_enrollment_code`), or — after too many
wrong attempts — 429 (`enrollment_locked`), each with a machine-readable
`error` code — see `src/hosted-interface.js:1055-1101`.

## 2. Authenticated requests

Every route below (everything except §1.3's exchange) requires **both**
headers on every request:

```
Authorization: Bearer <nodeToken>
X-OpenAGI-Node-ID: <nodeId>
```

The daemon authenticates the pair together (`nodeRegistry.authenticate`) and
checks the route against the phone's allowlist before authenticating at all
(`src/hosted-interface.js:697-728`). A bearer token alone, without the
matching node id header, is rejected — the token is scoped to that one node
id, not accepted for whichever id is convenient.

## 3. Route allowlist

`src/mobile-node.js`'s `isMobileRouteAllowed(method, pathname)` is the single
enumerated answer to "what may a phone token do." Read that function, not
this table, if the two ever disagree — but as of `136c15b` it allows exactly:

| Method | Path | Notes |
|---|---|---|
| GET | `/mobile/summary` | §4 |
| GET | `/tasks` | list, with `?queue=&bucket=&status=&limit=` |
| POST | `/tasks` | create a task |
| GET | `/tasks/:id` | one task |
| PATCH | `/tasks/:id` | partial update |
| DELETE | `/tasks/:id` | delete |
| POST | `/tasks/:id/complete` | §5 |
| GET | `/tasks/clarifications` | pending "ask me" queue |
| POST | `/tasks/clarifications/:id/answer` | body `{"answer": "..."}` |
| GET | `/pending-actions` | §6, `?status=pending` etc. |
| POST | `/pending-actions/:id/approve` | §6 |
| POST | `/pending-actions/:id/deny` | §6, body `{"reason": "..."}` optional |
| POST | `/message` | send a chat message to the agent; body limited to `{text, from?, sessionId?}` |
| GET | `/events` | §7, Server-Sent Events stream |
| GET | `/brief/today` | daily brief |
| POST | `/brief/focus/dismiss` | dismiss a brief focus item, body `{"key": "..."}` |
| GET | `/recap/daily` | daily recap |
| GET | `/plan/daily` | daily plan |
| GET | `/outreach/digest` | `{"digest": ...}` |
| POST | `/nodes/heartbeat` | §8 |
| POST | `/nodes/revoke` | §9 |
| POST | `/nodes/speech-token` | **allowlisted but not yet implemented — see below** |

`:id` above means a task/action id as minted by `createId()`:
`[a-zA-Z0-9_-]{1,120}`, deliberately excluding `.` and `/` so no id can carry
a path segment. `..` and `//` anywhere in the path are refused outright
(`src/mobile-node.js:15-49`). Everything not on this list — `/memory`,
`/skills`, `/computer-use/log`, `/control/restart`, `/nodes/g2/*`, etc. — is
refused for a mobile-scoped token even though it may be reachable to the
daemon owner or to a G2 node's own token.

> **Known gap:** `POST /nodes/speech-token` is present in the allowlist but
> the daemon has no route handler for that exact path (only
> `/nodes/g2/speech-token`, the G2 wearable's route, exists). Calling it
> currently 404s. Verified live against the daemon (`{"error":"not-found"}`,
> `src/hosted-interface.js` has no handler matching `pathname ===
> "/nodes/speech-token"`). Do not build a client feature against this route
> until a daemon change adds the handler.

## 4. `GET /mobile/summary`

The single round-trip a home-screen widget makes. No body; only the two
headers from §2.

```
GET /mobile/summary
Authorization: Bearer <nodeToken>
X-OpenAGI-Node-ID: <nodeId>
If-None-Match: "<etag from last response>"   (optional)
```

Response (`src/mobile-summary.js`, pinned by
`mobile/fixtures/summary-populated.json` and `summary-empty.json`):

```json
{
  "generatedAt": "2026-09-20T01:35:49.788Z",
  "today": [
    {
      "id": "task_5701146fe8184bfa",
      "title": "Ship the widget",
      "bucket": "today",
      "status": "pending",
      "priority": 80,
      "dueDate": null,
      "overdue": false
    },
    {
      "id": "task_e6a7d27f120b461c",
      "title": "Renew the domain",
      "bucket": "today",
      "status": "pending",
      "priority": 40,
      "dueDate": "2020-01-01T00:00:00.000Z",
      "overdue": true
    }
  ],
  "counts": {
    "today": 2,
    "this_week": 1,
    "overdue": 1,
    "pendingActions": 0
  },
  "pendingActions": [],
  "brief": {
    "headline": "2 things today, 1 overdue"
  }
}
```

Field notes, because these two objects are the most drift-prone thing in the
whole protocol:
- `counts` has **exactly four keys**: `today`, `this_week`, `overdue`,
  `pendingActions`. `this_week` carries an underscore; `pendingActions` is
  camelCase. **This asymmetry is deliberate — do not normalize it.** iOS
  decodes `this_week` into a `thisWeek` Swift property via a custom
  `CodingKey`; Android's Kotlin `Counts` data class declares the wire name
  directly. Both already depend on this exact mix.
- `today` is capped at 20 entries (`MOBILE_SUMMARY_MAX_TASKS`), sorted by
  priority descending, tie-broken by `createdAt` ascending. Only tasks in
  bucket `today` with status `pending`/`in_progress`/`blocked` are included.
  `?limit=N` on the request narrows this (1..20).
- `overdue` on a task item is `true` when `dueDate` is set and is in the past
  as of `generatedAt` — computed server-side; the client does not need to
  compare dates itself.
- `pendingActions` (the array) is capped at 5 entries
  (`MOBILE_SUMMARY_MAX_ACTIONS`); `counts.pendingActions` (the number) is the
  full pending count, uncapped.
- `brief.headline` is one human-readable sentence assembled server-side
  ("2 things today, 1 overdue, 3 waiting on you").

### ETag / 304

The response carries an `ETag` header computed over the **entire payload
except `generatedAt`** (`summaryETag`, `src/mobile-summary.js:59-64`):

```js
const { generatedAt, ...stable } = payload;
etag = '"' + sha256(JSON.stringify(stable)).base64url().slice(0, 27) + '"'
```

Send it back as `If-None-Match` on the next poll. If nothing else changed,
the daemon returns `304` (Not Modified) with no body — even though
`generatedAt` itself is always different (it's `now.toISOString()` at request
time). This is the whole point: a home-screen widget that polls every few
minutes gets a 304 (near-zero bytes, no re-render) on every call where
nothing actually changed, and only pays for a full body when something did.
Do not compute your own client-side "did anything change" check against
`generatedAt` — it always differs and will defeat the cache. The response
also sets `Cache-Control: no-store`, so this ETag mechanism — not the
browser/URL cache — is the only freshness signal to rely on.

## 5. Completing a task

```
POST /tasks/:id/complete
Content-Type: application/json
Authorization: Bearer <nodeToken>
X-OpenAGI-Node-ID: <nodeId>

{"completedVia": "mobile"}
```

**Every mobile-originated completion sends `"completedVia": "mobile"`.** This
is how the daemon (and anything reading task history later) distinguishes a
completion made from the phone from one made by the CLI, the dashboard, or
the agent (`"manual"` is the default if `completedVia` is omitted —
`src/hosted-interface.js:2591-2596`).

Response is the full updated task, verified live against the daemon:

```json
{
  "id": "task_4c91be54ad9845d1",
  "queue": "user",
  "title": "Pack for the trip",
  "description": "",
  "bucket": "done",
  "priority": 50,
  "category": null,
  "tags": [],
  "source": "manual",
  "sourceId": null,
  "sourceUrl": null,
  "sourceMeta": null,
  "status": "completed",
  "dueDate": null,
  "scheduledFor": null,
  "parentGoalId": null,
  "dependsOn": [],
  "createdAt": "2026-09-20T01:40:13.150Z",
  "updatedAt": "2026-09-20T01:40:13.181Z",
  "completedAt": "2026-09-20T01:40:13.181Z",
  "completedVia": "mobile"
}
```

Completing moves `bucket` to `"done"` and `status` to `"completed"` as a side
effect — the client does not need to also PATCH those fields. A `task-updated`
SSE event (§7) fires for every other connected client (including the phone's
own widget) as a result.

`GET /tasks?queue=user` returns the full task shape above for every task —
pinned by `mobile/fixtures/tasks-list.json` — as `{"tasks": [...], "stats":
{...}}`. Valid `bucket` values: `today | this_week | this_month |
this_quarter | this_year | someday | done`. Valid `status` values: `pending |
in_progress | blocked | completed | cancelled`. Valid `queue` values: `user |
agent` (`src/task-store.js:22-24`). A phone only ever reads/writes the `user`
queue in practice, but the daemon does not enforce that at the route level —
pass `queue=user` explicitly.

## 6. Approvals

The agent queues a `pending-action` when it wants to run a tool flagged
`needsConfirmation: true` (sending an email, running a shell command, etc.).
The phone is one of the surfaces that can approve or deny it.

```
GET /pending-actions?status=pending
Authorization: Bearer <nodeToken>
X-OpenAGI-Node-ID: <nodeId>
```

Response — verified live against the daemon:

```json
{
  "actions": [
    {
      "id": "act_840d87422622443a",
      "toolName": "send_email",
      "args": { "to": "someone@example.com" },
      "context": null,
      "summary": "Send an email to someone@example.com",
      "reason": null,
      "dedupeKey": null,
      "status": "pending",
      "createdAt": "2026-09-20T01:40:25.625Z",
      "expiresAt": null,
      "decidedAt": null,
      "decidedBy": null,
      "result": null,
      "error": null
    }
  ]
}
```

(`mobile/fixtures/pending-actions.json` pins the empty-list shape,
`{"actions": []}`, because the fixture daemon has nothing pending; the object
shape of one action above was captured live for this document, not from that
fixture.)

**Approve:**

```
POST /pending-actions/:id/approve
Authorization: Bearer <nodeToken>
X-OpenAGI-Node-ID: <nodeId>
```

No body. The daemon re-invokes the original tool with the confirmation bypass
and returns that tool's own invocation result — `{"ok": true, "result": ...}`
on success or `{"ok": false, "error": "..."}` on failure — optionally with a
`continuation` field if another step follows. This shape varies by which tool
was approved; there is no single fixed schema beyond the `ok`/`error`
envelope (`src/hosted-interface.js:2181-2224`).

**Deny:**

```
POST /pending-actions/:id/deny
Content-Type: application/json
Authorization: Bearer <nodeToken>
X-OpenAGI-Node-ID: <nodeId>

{"reason": "not now"}
```

`reason` is optional (defaults to `"denied by user"`). Response is exactly
(`src/hosted-interface.js:2226-2241`, verified live):

```json
{ "id": "act_840d87422622443a", "status": "denied" }
```

Approving or denying an action that is no longer `"pending"` (already decided,
claimed, or expired) returns `409`; approving an expired one returns `410`.

## 7. Server-Sent Events (`GET /events`)

```
GET /events
Accept: text/event-stream
Authorization: Bearer <nodeToken>
X-OpenAGI-Node-ID: <nodeId>
```

Long-lived connection. Frame format (`handleSse`, `src/hosted-interface.js:3327-3342`):

```
event: <name>
data: <json>

```

An immediate `event: hello` frame confirms the connection; a `: ping` comment
frame arrives every 15s to keep intermediaries from timing the connection
out (not a named event — clients should ignore comment lines, i.e. any line
starting with `:`).

The event names a mobile client reacts to:

| Event | Fires when |
|---|---|
| `task-updated` | a task is created, updated, completed, or deleted — `{op: "create"\|"update"\|"delete", task}` |
| `task-reminder` | a due/overdue task reminder fires |
| `task-auto-changed` | the proactive observer changes a task's status/bucket automatically |
| `pending-action` | a new approval is queued |
| `pending-action-resolved` | an approval is approved/denied/expired (by any client, including another device) |
| `clarification-created` | the agent needs the user to answer a question |

A phone should refresh its local task/summary cache and its widget's data on
`task-updated`, `task-auto-changed`, and `pending-action-resolved`; surface a
notification/badge on `pending-action` and `clarification-created`; and
consider `task-reminder` a candidate for a local push notification.

`GET /events` is only practical while the app is foregrounded/backgrounded
with an active connection (no APNs/FCM push bridge exists in this phase) —
polling `GET /mobile/summary` on the heartbeat cadence below is the
foreground-independent fallback for widgets.

## 8. Heartbeat

While foregrounded, the phone should call this roughly every 30 seconds so
the daemon's node roster shows it as recently seen — the same cadence the
existing node clients use.

**The full request the daemon actually requires** (verified live against the
daemon — a body of only `{"nodeId": "..."}` gets `400 {"error":"nodeId and
name are required and must be non-empty strings"}`):

```
POST /nodes/heartbeat
Content-Type: application/json
Authorization: Bearer <nodeToken>
X-OpenAGI-Node-ID: <nodeId>

{
  "nodeId": "mobile:D3B1F6C2-...",
  "name": "Sean's iPhone",
  "role": "node",
  "url": null,
  "version": "1.0.0",
  "build": null,
  "buildSource": null,
  "capabilities": []
}
```

Required fields: `nodeId` (must equal the `X-OpenAGI-Node-ID` header, or the
daemon returns `403`), a non-empty string `name`, and `role` which must be
the exact literal `"node"`. `url`, `version`, `build`, `buildSource` are
optional strings (or `null`); `capabilities` is an optional array.
(`src/hosted-interface.js:1119-1165`.)

Response, verified live:

```json
{ "ok": true, "capabilities": [] }
```

## 9. Revocation

The phone can log itself out (equivalent to "sign out this device"):

```
POST /nodes/revoke
Content-Type: application/json
Authorization: Bearer <nodeToken>
X-OpenAGI-Node-ID: <nodeId>

{"nodeId": "mobile:D3B1F6C2-..."}
```

`nodeId` in the body must equal the header's node id or the daemon returns
`403`. Response: `{"ok": true, "revoked": true}`
(`src/hosted-interface.js:1203-1211`). After this call the daemon's stored
credential for that node is gone; the phone should delete its own stored
`nodeToken`/`nodeId` at the same time and treat itself as unpaired.

The daemon owner can also revoke a phone from the dashboard/CLI
(`POST /nodes/<nodeId>/revoke`, an owner-only admin route, not on the mobile
allowlist) — a client should be built expecting that its credential can
become invalid at any time from the other end, and every route in this
document can return `401`.

## 10. Cleartext host allowlist

The pairing deep link and every subsequent request must use `https://`
**unless** the daemon's host is one of:

- a Tailscale MagicDNS name — anything ending in `.ts.net`
- a Tailscale CGNAT address — `100.64.0.0/10` (i.e. `100.x.y.z` where
  `64 <= x <= 127`)
- an RFC1918 private address:
  - `10.0.0.0/8` (any `10.x.y.z`)
  - `192.168.0.0/16` (`192.168.x.y` only — not any `192.x`)
  - `172.16.0.0/12` (`172.16.x.y` through `172.31.x.y` — not any `172.x`)

Anywhere else, cleartext `http://` is refused. `127.0.0.1`/`localhost` is
refused unconditionally regardless of scheme — a phone can never reach the
daemon's own loopback address, so pairing against it is always a mistake, not
just an insecure one. This exact table is implemented once in
`src/pair-phone.js` (`isTailnetHost`, `isPrivateLanHost`,
`assertPhoneReachable`) on the daemon/CLI side, and **both mobile clients
implement the identical table independently** so a phone refuses to dial an
address the daemon itself would have refused to hand out. Do not loosen or
"simplify" this table on either platform — the boundaries above (`192.168`
not `192.*`, `172.16-31` not `172.*`, CGNAT's `100.64-127` not `100.*`) are
exact and were chosen to match RFC1918/Tailscale's real ranges, not
approximate them.
