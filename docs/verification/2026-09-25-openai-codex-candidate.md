## Remaining gates

1. `inspectReadiness()` still ends at `canary-required`; no evidence-bound transition to `chat-ready` exists. Do not replace it with a cosmetic status write. Source review of Codex 0.156.1 explains the recorded `config/read.features.unified_exec=false` versus `experimentalFeature/list.unified_exec.enabled=true`: normal configuration opt-outs are [normalized back on](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/core/src/config/managed_features.rs#L153-L168) unless a managed requirement pins the feature. The separate `features.shell_tool=false` gate removes built-in command tools in upstream [tool-planner tests](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/core/src/tools/spec_plan_tests.rs#L1099-L1138); disabling `unified_exec` alone does **not** remove them. These source observations are not proof of the installed binary's actual per-thread tool plan. Require a thread-scoped feature check, exact-version tool-plan evidence that `exec_command` and `write_stdin` are absent (including code mode), and a live negative command canary with an independent positive control; reject `command/exec` RPC separately. Do not weaken the existing disagreement gate on source reasoning alone. Qualify the exact binary, config, account, model, blocked built-ins, negative canaries and successful real turn together. The default remains unchanged.
2. The broker requires the plaintext TLS ClientHello SNI to match CONNECT before dialing and rejects ECH, in addition to hostname, public resolved IP and port. An independent read-only review of this exact SNI design returned **NO-GO against an exact HTTPS-authority requirement**: the tunnel **cannot inspect encrypted HTTP `Host`/HTTP/2 `:authority`**. A later explicit user response authorized adopting a narrower *design target*: trust the pinned official Codex HTTP client to choose its URL authority, with the OS namespace and broker constraining the transport. See `docs/verification/2026-09-25-codex-network-trust-model-study.md`. This does not prove the boundary is implemented/qualified, change served-model evidence, or permit activation; independent design and exact-candidate reviews and negative canaries remain open. The two candidate hosts are not a vendor-guaranteed exhaustive egress allowlist; reject additional destinations rather than silently widening it.
3. The binary verification is descriptor-bound across pathname replacement, and the profile mount is descriptor-bound. The executable itself and its runtime dependencies are not an immutable release artifact; verify the exact installed candidate at activation, re-review sandbox/relay and process-tree behavior, and ensure private profile storage is on a permissions-preserving filesystem.
4. No login or inference used the user's ChatGPT session. There is no observed entitlement, served model or usage from a live turn; no production readiness is claimed. In the 0.156.1 protocol, [`Thread.model` and `.reasoning_effort` explicitly are not per-turn execution telemetry](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/app-server-protocol/src/protocol/v2/thread_data.rs#L242-L249); `turn/completed` and turn usage do not attest model/effort, and the absence of `model/rerouted` proves nothing about the served model. Keep requested model and effort, thread snapshot, reroutes, turn-bound usage, and any backend accounting distinct; do not fabricate `observedModel` from a request or thread snapshot. A single-use thread's estimated, model-labelled usage may corroborate a live turn, but does not replace authoritative per-turn attribution. Browser callback login is disabled inside the network namespace; device authorization still requires the user's action on the official site after technical preflight. `account/login/start` with device-code would itself POST to the issuer, not merely test reachability; it has not been called on the real candidate. Fallback after a dispatched timeout or app-server exit is denied because absence of visible text does not prove absence of an upstream effect.

A RED/GREEN correction now denies the route unless the provider reports a pre-login receipt **and** denies direct production-client login unless its private receipt exists; closing the client clears it. ## Online follow-up: served-model and effort evidence

After the owner explicitly retained the verification requirement, a read-only review of the [official Responses event contract](https://developers.openai.com/api/reference/resources/responses/streaming-events), the [Response object](https://developers.openai.com/api/reference/resources/responses), and the [exact Codex 0.156.1 parser](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/codex-api/src/sse/responses.rs#L408-L415) identified a possible source: the server's per-response `response.model` and, **if present**, `response.reasoning.effort`, correlated with the response ID. The API calls `response.model` the model ID used to generate the response; returned effort is a **server-reported reasoning configuration**, not independent proof of how much reasoning was performed. Whether the ChatGPT-backed stream consistently supplies both fields remains untested. In Codex 0.156.1, `response.created` forwards only the ID and [`response.completed` forwards ID, usage and end-turn](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/codex-api/src/sse/responses.rs#L490-L506). The [official 0.157.1 app-server notification schema](https://github.com/openai/codex/blob/36650394c5b38c2990ccf2a3457165ca3e9d9726/codex-rs/app-server-protocol/schema/json/v2/RawResponseCompletedNotification.json) still has neither model nor effort. Upgrading to that inspected release alone does not fill the gate; no authenticated observation was made.

A candidate upstream change would extract a minimal, validated `(responseId, serverReportedModel, serverReturnedConfiguration)` inside Codex's own TLS client, propagate it through core and a versioned app-server notification to OpenAGI, and reconcile every response of a turn (including multiple responses and any reroute). **This alone would still not attest effective effort**: OpenAI would also need to define and supply that semantic value for ChatGPT/Codex responses. Reject missing or conflicting values instead of filling them from requested settings or traces. Qualify the HTTP SSE and WebSocket paths independently, avoid logging raw responses or headers, and review/pin any custom Codex build and its dependencies before authentication. This is a **proposal**, not an implemented or tested attestation; even the server's report cannot independently prove model weights or actual compute. The official SDK/CLI JSON and the existing app-server notification do not provide a substitute. The user's refusal to downgrade the gate supersedes the earlier timed-out question: keep activation blocked until a source with the required provenance is implemented and verified.

### Design-consensus correction (2026-09-26)

The L3 design debate found that extraction of `response.reasoning.effort` **alone cannot qualify the retained requirement**. The public Response schema calls `reasoning` *configuration options*, and neither a live capture nor equality with the requested setting can determine whether the returned value reports effective effort or merely echoes configuration. A provider-defined, response-bound *effective* reasoning-tier contract for authenticated Codex/ChatGPT traffic and an official Codex `app-server` propagation event are separate upstream dependencies; both are missing from the versions examined. Until those exist, label the field `serverReturnedConfiguration`, never `observedEffort`, and keep BLOCK / NOT QUALIFIED. A downstream Codex fork would change the approved pinned-official-client trust model and cannot repair the missing provider semantics by itself. The proposed receipt binds a locally reserved attempt ID, upstream response ID, turn and output fragments, handles dispatched attempts with no ID as uncertain, rejects WS connection headers as per-response proof, and buffers text within strict bounds before verified delivery. The full, still-provisional review is in `workspace/consensus/2026-09-26-openagi-served-model-consensus/consensus_report.md`. This debate did not involve login, inference or activation; the existing service was still active at the last check.

### Fail-closed implementation increment (2026-09-26)

OpenAGI now treats `model/rerouted` as an indication only, not an `observedModel` receipt. The app-server client discards provisional text deltas and only sends the final message after a successful terminal turn; a failed turn emits no text. A separate unconditional production-side `CODEX_ATTESTATION_REQUIRED` guard rejects `runChatTurn` before creating a profile or dispatching a request until an official provider-defined effective-effort contract, matching app-server notification and qualification are actually implemented. This guard is deliberately not an issuer or a way to mark the provider ready. Credential-free fake-server tests proved each behavior RED before the narrow fixes and then GREEN. Terminal text is held until the start acknowledgement matches, and terminals with missing or contradictory identities are rejected. A duplicate terminal delivered in the same parsed batch is rejected; a later duplicate **after** callback delivery cannot retract text already exposed. ### Active feasibility search, not passive monitoring (2026-09-26)

Three independent read-only investigations compared current official Codex app-server, TypeScript/Python SDK and `codex exec --json` surfaces, the Responses object/retrieve endpoint, and Hermes Agent's two Codex integrations. They found no *inspected public interface* satisfying the retained requirement of a provider-authored, per-response **effective** reasoning tier while Codex retains OAuth custody and OpenAGI controls tools. This is a scoped interface finding, not a statement about undocumented private capabilities. No authenticated probe or production qualification occurred.

- [Responses specifies](https://developers.openai.com/api/reference/resources/responses) `model` as the ID used to generate the response, but calls `reasoning` *configuration options*. [The reasoning guide](https://developers.openai.com/api/docs/guides/reasoning#reasoning-effort) says the effort parameter *guides* the model and reasoning adapts to the task; a returned configuration, reasoning-token count or transcript cannot attest an effective per-response tier. By contrast, the same Response reference explicitly identifies `service_tier` as the processing mode actually used; no equivalent wording was found for effort.
- The inspected [official `rust-v0.157.1` raw-response notification](https://raw.githubusercontent.com/openai/codex/36650394c5b38c2990ccf2a3457165ca3e9d9726/codex-rs/app-server-protocol/schema/json/v2/RawResponseCompletedNotification.json) contains response/thread/turn IDs and usage, not model/effort. Codex's [SDK](https://developers.openai.com/codex/codex-sdk) and [app-server](https://developers.openai.com/codex/app-server) do not document an alternative response-bound effective-effort receipt. The app-server documentation also calls its command/transport experimental and unsupported for production workloads; this adds a maturity gate separate from the missing receipt.
- [Hermes's default Codex provider](https://github.com/NousResearch/hermes-agent/blob/42457cc23378203218a674cd766f1552a43d6bb4/plugins/model-providers/openai-codex/__init__.py) uses host-owned OAuth/Responses, which changes the stipulated token-custody boundary. [Its optional app-server runtime](https://hermes-agent.nousresearch.com/docs/user-guide/features/codex-app-server-runtime) keeps Codex custody but retains Codex's agent/tool loop. Neither establishes the requested triple guarantee for OpenAGI.

Why local work cannot close this particular gate: if two upstream executions have different effective tiers but identical request, response configuration, text, IDs, token counts and app-server events, OpenAGI sees the same input in both and must give the same verdict. A local signature, proxy, SDK change, fixture, or telemetry correlation cannot distinguish them. A sufficient change would be a provider-defined response-bound effective-tier declaration (or explicit unavailable state) propagated by an official versioned Codex event, followed by security and delivery qualification. A local fork could transport a newly defined field but cannot define the missing upstream semantics; directly querying the documented `/responses/{id}` uses an API-key contract and does not grant access to Codex's ChatGPT subscription responses. The presently feasible product is to report requested/configured values with **effective tier unknown**, but doing so would relax the owner's required gate and has **not** been authorized. Therefore production stays blocked rather than silently adopting that alternative.

## Network trust-model decision and limits

Two independent read-only architecture checks found no configuration-only way for stock Codex 0.156.1, an opaque CONNECT tunnel and OS IP/port isolation to **independently prove** the exact encrypted HTTP authority without crossing the credential boundary. [HTTP/2 permits multiple authorities on one TLS connection, including a CONNECT tunnel](https://www.rfc-editor.org/rfc/rfc9113.html#section-9.1.1); matching CONNECT and SNI does not bind each HTTP request. This is a protocol possibility, not a demonstrated exploit against the two candidate hosts. The [Codex managed network proxy](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/network-proxy/README.md) distinguishes opaque full-mode CONNECT from method-enforcing TLS interception; the read-only limited mode cannot support the OAuth POSTs. Workspace routing may introduce more backend hosts, which the current candidate intentionally denies until reviewed.

The user authorized the narrower network model as a **design target only**; the other direction remains the stricter alternative if later review fails. Neither changes the active provider or the separate model-attribution gate:

- Retain exact independently enforced HTTPS authority and Codex-only token custody: keep this stock build **NO-GO**. No qualifying external mechanism was established without TLS interception. A custom, pinned and audited client-side authority policy over every Codex authentication/refresh/backend request would change the trusted computing base, **not** independently enforce it against a compromised Codex child. Treat that as a new architecture requiring separate threat-model and design review, not as a drop-in fix or permission to start login.
- Accept a narrower boundary for this specific stock runtime: trust the pinned official Codex HTTP client to choose its own URL authority, while the OS namespace plus broker restricts CONNECT/SNI/public IP. This is **not** independent exact-origin enforcement and cannot be represented as such. An explicit revision of the design, threat model, tests and review remains required before any login, despite the owner's subsequent operational authorization.

TLS interception could inspect the authority but necessarily handles decrypted credential-bearing requests outside Codex and conflicts with the chosen no-token-exposure boundary. Merely adding more SNI, DNS or certificate checks cannot establish an encrypted request's `Host`/`:authority`. The provider and service remain unchanged pending full qualification; operational authorization does not waive the pre-login technical gate.

The ChatGPT subscription and the OpenAI API key are distinct; no OAuth token values, prompts, responses, or private credential files are retained in this document.
