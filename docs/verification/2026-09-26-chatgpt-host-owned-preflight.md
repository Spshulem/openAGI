## Scope and change

- The prior default lock under `~/.local/state/openagi` was outside the installed core service's `ReadWritePaths` and had a mode-0755 parent. A RED test reproduced failure when the legacy directory was unwritable. The candidate keeps the owner-only OAuth file in `~/.openagi/chatgpt-host-oauth/chatgpt-oauth.lock`, a private child of the core user service's already writable data root; the **kernel-lock anchor** is now the canonical OS account HOME directory (see below), not this replaceable file. It does not widen `ProtectHome`, `ReadWritePaths`, or the companion RPC trust boundary. Both the user-mode and system-mode unit generator in `scripts/install-systemd.sh` create and grant their respective service `~/.openagi` root; the retained source does not revise the system-mode generator, and no installed unit was changed.
- A real sandbox-like synthetic probe exposed an independent HIGH flaw: the old `/usr/bin/flock -x -w 20 3 /usr/bin/sh ...` command interpreted `3` as a **relative pathname**, not the inherited FD 3. The resulting lock could be in the checkout CWD, not on the intended inode; a read-only CWD made acquisition fail. RED test: child process with read-only CWD and a separate writable lock path. The unrelated pre-existing untracked file named `3` in the checkout was **not** removed or read; its provenance was not established.
- The first fix kept a shell alive during the critical section. An independent read-only review found two further HIGH risks in those bytes: loss of that shell could release the lock while the Node callback continued, and an untrusted writer of the ancestor directory could replace the private subdirectory and split the lock inode. RED tests preceded each correction. The current candidate invokes `flock -x -w 20 3` **without a command** on an inherited FD, waits for the helper to exit successfully, then keeps the parent Node file description open throughout the callback; closing the parent or killing it releases the kernel lock. It rejects an owner-mismatched, group/other-writable or symlinked data-root directory before entering the critical section. The private lock directory is still owner-only; its file is opened with `O_NOFOLLOW` and checked for owner, type, link count and mode, but is not the kernel-lock anchor.
- A second read-only review accepted the helper lifetime fix but found a remaining conditional HIGH: a writer of the *parent of* `.openagi` could rename the entire data root and split the lock inode. In this checkout `namei -l` showed mode 0777 on the project tree (while an earlier root-owned mount ancestor restricted traversal), and mode 0700 on the current user HOME and `~/.openagi`; this is not an exploit claim about the installed service. A RED test reproduced the permissive-parent case. The local code now rejects group/other-writable or untrusted-owner ancestors before creating `.openagi`; it allows the systemd `ProtectHome=read-only` ownership masking of `/home` only with the read-only mount confirmed in `/proc/self/mountinfo`. The transient preflight initially rejected the mapped `/home` owner until this bounded exception was added. At that review point, system-mode installation still used the project tree as HOME and had not been changed or qualified; that mode-0777 tree would fail this guard as a data root. An attempted source-only installer revision was later withdrawn after independent security review; no system installation was performed.
- The **2026-09-27 independent review of those later bytes found another HIGH**: a cooperating or adversarial process with the *same UID* can rename even owner-only `.openagi` during a critical section; a second lock-path resolution opens a different inode. A credential-free, disposable private-tree probe with two concurrent calls **in one process** reproduced the inode split (`secondEnteredWhileFirstActive:true`, exit 0), then removed its tree. This confirms the pathname race, not a separately exercised malicious process or cross-UID exploit. No existing `.openagi`, credential, wallet item or installed service was touched. A RED regression then reproduced the same failure in the repository. The local repair locks the *canonical OS account HOME inode* through a read-only descriptor inherited by `flock`; it requires that HOME belong to the service UID and that **all ancestors above it** be root-owned and not group/other-writable (or the uniquely verified read-only systemd `/home` bind). Another same-UID process cannot rename that anchor under this declared boundary; renaming `.openagi` during the callback no longer admits a second holder in the regression. Kernel `flock` on this read-only directory was also exercised successfully under a transient `ProtectHome=read-only` unit. This is a **local repair, not independent acceptance**: a malicious process with the same UID can still access resources outside this advisory lock, and the legacy system-mode project tree is not qualified. The same review found that `/proc/self/mountinfo` accepted any `ro /home` entry even if a conflicting `rw` overlay exists (conditional), and that tests depended on the Hermes-private `TMPDIR` and merely observed a contender child PID. A source/parser regression now rejects multiple `/home` mount entries; lock fixtures use private directories under the test user's HOME so `TMPDIR=/tmp` also passes, and the two-process test observes a blocked waiter for the actual kernel-lock inode in `/proc/locks`.
- A further read-only review found that checking only the immediate HOME parent left a conditional nested-HOME rename route; a synthetic ancestor-matrix test now rejects a parent owned by root below a grandparent owned by the service UID, and the source checks each HOME ancestor up to `/`. The same review found system-mode `scripts/install-systemd.sh` then set the dedicated user's HOME to `PROJECT_DIR` without guaranteeing that HOME itself was owned by the service UID or had a root-stable parent; a root-owned checkout or this mode-0777 project tree fails closed under the candidate guard. A source-only installer experiment attempted a dedicated `/var/lib/openagi` HOME and render-only previews. Independent review found privileged unit-directive injection, a root-read environment-file symlink boundary, legacy-state loss, missing restart/rollback and configuration ambiguity. That experiment and its test were reverted in full; the original installer remains unchanged and **system-mode installation remains NOT QUALIFIED**. No system account or installed unit was changed. It also noted that `HOME` environment data-path selection can diverge from `os.userInfo().homedir` anchor selection: this does not split the anchor, but may deny access to the data path. Pre-lock pathname operations are not a descriptor-relative proof against a same-UID swap; they carry no token data, and the stable anchor protects cooperating credential effects. Finally, this Linux-only test file now skips on other platforms (verified by a simulated Darwin test run: 17 skipped, not a native macOS run).
- The **final exact-byte read-only review** found a remaining **conditional HIGH outside the proven mount topology**: a same-UID actor able to remount or bind-mount a different directory over the canonical HOME in another mount namespace can open a different HOME inode and obtain an independent `flock`, even though `/home` itself is root-owned and non-writable. The ancestor matrix only tests the pure predicate, not an actual HOME mount replacement. No such replacement or credential operation was performed. `openagi.service` was observed with `NoNewPrivileges=yes` and zero effective capabilities, but `RestrictNamespaces=no`; this does not prove that *all* same-UID processes participating in the same Secret Service grant use the same mount topology. The current lock guarantees cooperating callers sharing the stable HOME inode; it is **not qualified as an adversarial same-UID cross-namespace lock**, and the remaining HIGH must not be silently treated as closed. In one credential-free child namespace probe on this Fedora host, `unshare --user --map-current-user --mount` succeeded, but `mount --bind /home /home` returned `must be superuser`; a second no-write probe of `withKernelLock` failed closed on an unsafe mapped ancestor. These observations do not prove a universal denial of mount replacement or the installed candidate's sandbox. The installed service remains on the previous release. A user-namespace/mount capability and threat-model decision is required before asserting a stronger guarantee; weakening the invariant to make the source test green is not acceptance.
- The source change does not issue a pre-login admission receipt. The HTTP login path remains hard-denied by default, the provider refuses production inference, and setup/admin selection remains blocked. Moving the lock is a prerequisite repair, not a reason to turn on a dormant qualification flag.
